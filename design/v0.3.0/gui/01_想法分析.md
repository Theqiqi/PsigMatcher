# 01 想法分析（v0.3.0）

- 版本：v0.3.0
- 输入：`.idea/v0.3.0.md`
- 模式：**修改/添加功能**（对 v0.2.4 现有程序做增量修改；非新建程序）
- 涉及模块/界面：psig 静态库（内存扫描、进度回调）、GUI（扫描 ViewModel、状态栏进度显示）

## 一、输入模式判定

想法描述的是对现有 `psig_gui` + `psig` 的**性能与进度反馈改进**，不是全新程序。故本流程为**修改型流程**：
- 复用 `.flow/带GUI的单体程序的GUI入口系统.md` 与 `.flow/带GUI的单体程序的业务系统静态库.md` 中与改动相关的步骤（需求→设计→编码→审查→编译→测试），仅执行受影响部分。
- 每个分析文档标注「改动点」；未受影响的既有内容只引用既有文档，不重复分析。

## 二、改动点清单

| 编号 | 原始想法 | 类型 | 涉及模块/界面 |
| --- | --- | --- | --- |
| C-01 | 扫描进度条恒为满格（100%），等于没用 → 修复为真实已完成量/总量 | 修复 | psig（进度语义）、GUI（进度取值） |
| C-02 | 扫描为「进程×区域」双重串行，速度慢 → 按内存区域分块，交多线程并行扫描 | 改进 | psig（扫描执行） |
| C-03 | 每读一块内存就刷新一次界面，回调过密会拖慢扫描 → 改用定时器（约 100~200ms）定期采样进度 | 改进 | GUI（扫描 ViewModel、状态栏） |
| C-04 | 每次回调都跨线程投递界面事件、每次刷新都重设样式表 → 工作线程只更新原子变量，界面定时读取 | 改进 | GUI（进度投递链路） |
| C-05 | 明确**不**新增「可读/可写/可执行区域过滤」选项 | 范围界定 | —（排除项） |

## 三、逐条分析与期望行为

### C-01 进度条恒为 100%（进度语义错误）
- **现状**：`psig::ScanProcesses()` 的进度回调在 `api/process_scan.cpp` 内构造 `ScanProgress`：
  ```cpp
  sp.done  = total;   // total = patterns.size()（特征码个数）
  sp.total = total;
  ```
  `done` 与 `total` 被赋成同一个值（特征码个数），GUI 侧 `pct = sp.done * 100 / sp.total` 恒为 100%。
- **表现**：扫描进度条从开始到结束始终满格，无法反映真实进度。
- **期望**：进度应反映**真实工作量**：以「已完成工作量 / 总工作量」表达，随扫描推进单调增长；扫描开始接近 0%，结束达到 100%。
- **根因线索**：`ScanProgress` 现有字段注释为「已处理模式数 / 总模式数」，与"扫描进度"语义不符；且回调发生在 `ScanRegion` 的 **1MiB 分块循环**内，粒度过细而数值错误。

### C-02 按内存区域并行扫描
- **现状**：`ScanProcesses()` 对 `req.pids` 逐个进程串行；`ScanOneProcess()` 内 `for (const auto& region : regions)` 再逐区域串行。即「进程 × 区域」双重串行，多核未利用。
- **期望**：把**内存区域**作为并行单位（区域之间相互独立、只读），分派给多个线程并行扫描，缩短总耗时。
- **依据（已澄清）**：选进程后的批量场景下跨进程并行收益有限（常只有 1 个进程），真正的并行轴在**进程内部的区域维度**；瓶颈常在 `ReadProcessMemory` 的 I/O 等待，并行可重叠等待。
- **约束/难点（待设计阶段细化）**：
  - 同一进程句柄被多线程并发 `ReadProcessMemory`（读操作线程安全）。
  - 命中结果需并发汇聚（各线程局部结果 → 结束合并，或加锁）。
  - `maxResultsPerPattern`（每模式命中上限）在并行下需协调，避免超限/少限。
  - 取消标志（`g_cancel` / `cancel` 出参）需被所有工作线程轮询。

### C-03 定时器采样进度
- **现状**：`gui/src/viewmodel/scan.cpp` 中进度回调 lambda 每被调用一次就 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 投递一个界面更新。
- **期望**：界面刷新频率与扫描循环**解耦**——用 `QTimer`（约 100~200ms）定期读取当前进度并刷新状态栏，而不是每完成一小块就刷新一次。
- **范围（已澄清）**：进度显示位置为**状态栏**（`QProgressBar` + 瞬时 `QLabel`），不是日志区（日志仅有开始/结束行）。

### C-04 减少回调
- **现状**：
  1. 进度回调在 `ScanRegion` 的 **1MiB 分块**内触发 → 一次扫描投递**成千上万**个排队界面事件。
  2. `MainWindow::setTransientMessage()` **每次都调用 `setStyleSheet()`**，代价高。
- **期望**：
  - 工作线程只更新**原子变量**（进度数值），不直接操作界面；界面由定时器（C-03）读取原子变量后刷新。
  - 进度回调的触发**粒度粗化**（至少不再按 1MiB 分块触发）。
  - 刷新瞬时信息时不重复重设样式表。

### C-05 不新增区域权限过滤（范围界定）
- **决策**：**不**新增「按可读/可写/可执行过滤区域」的选项。
- **理由**：可读是扫描的前提（否则读不到内存）；按可写/可执行过滤有**漏报**风险，而漏掉命中比扫得慢更糟糕。当前 `atomic::IsReadableProtect()` 已只保留可读区域，语义正确，不改。

## 四、本轮已澄清的设计决策（用户确认）

| 议题 | 决策 |
| --- | --- |
| C-02 并行轴 | 按内存**区域**分块并行（非跨进程） |
| C-03 刷新机制 | `QTimer` 定时采样（约 100~200ms），非每次回调刷新 |
| C-03 显示位置 | 状态栏进度条（+ 瞬时文字），非日志区 |
| C-04 回调策略 | 工作线程只写原子变量；界面定时读；粗化回调粒度 |
| C-05 区域过滤 | **不加**可读/可写/可执行过滤选项 |
| 线程池 | 非"必须"；本版本以区域并行 + 回调削减为主，线程数自适应 CPU |

## 五、不做的事（排除项）

- 不新建程序、不新增窗口/页面。
- 不改技术栈（沿用 Qt6::Widgets / Qt6::Concurrent / MSVC+Ninja / vcpkg）。
- 不改变扫描语义（命中判定、结果字段、导出格式均不变）。
- 不新增按可读/可写/可执行过滤区域的选项（C-05）。
- 不删除 psig 公共 API。
